# Оформление тестовых наборов — краткая шпаргалка

## 1. Структура тест-кейса

- **ID и название** — что именно проверяем.
- **Требование** — с каким пунктом спецификации связан тест.
- **Предусловия** — состояние системы до проверки.
- **Входные данные** — конкретные значения.
- **Действия** — воспроизводимые шаги.
- **Ожидаемый результат** — рассчитывается заранее и независимо от реализации.
- **Фактический результат** — что произошло при запуске.
- **Окружение** — версия программы, сборка, ОС, настройки и зависимости.
- **Статус** — `Passed` / `Failed`.

Другой человек должен суметь повторить тест без дополнительных вопросов.

## 2. Проектирование набора

- Разбить входные данные на **классы эквивалентности** и взять представителей.
- Проверить **границы**: значение перед границей, на ней и после неё.
- Добавить пустой и минимальный вход, некорректные данные и важные комбинации ошибок.
- Один тест должен проверять одно понятное поведение.
- Проверять повторные запросы, переходы состояний и идемпотентность, если это требуется.

## 3. GoogleTest

```cpp
TEST(DeliveryCostTest, ReturnsBasePriceForMinimumWeight) {
    // Arrange
    const int weight = 1;

    // Act
    const int actual = calculateDeliveryCost(weight, false);

    // Assert
    EXPECT_EQ(actual, 200); 
    // При выбросе ошибки (пример): EXPECT_THROW(func(), std::invalid_argument)
}
```

- `TEST(TestSuite, Scenario)` — отдельный тест.
- `EXPECT_*` фиксирует ошибку и продолжает текущий тест.
- `ASSERT_*` фиксирует ошибку и прекращает текущий тест.
- `EXPECT_THROW(expression, ExceptionType)` проверяет исключение.
- `TEST_F` и фикстура нужны для общей подготовки; каждый тест всё равно должен получать чистое начальное состояние.

## 4. Требования к хорошему набору

- **Трассируемость:** требование ↔ связанные тесты.
- **Независимость:** результат не зависит от порядка запуска тестов.
- **Воспроизводимость:** одинаковые вход и окружение дают одинаковый результат.
- **Детерминированность:** фиксировать seed; не зависеть от случайного времени, сети и чужих данных.
- **Версионирование:** тесты и их данные хранить в Git вместе с соответствующей версией кода.

Тест, который периодически падает без изменения кода, называется **flaky** и требует исправления.

## 5. При падении сохранить

- точный вход и шаги воспроизведения;
- ожидаемый и фактический результаты;
- версию программы и конфигурацию сборки;
- ОС, компилятор и версии важных зависимостей;
- логи, сообщение об ошибке и при необходимости stack trace.
