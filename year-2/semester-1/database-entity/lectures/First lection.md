# Первая лекция. Данные и роль СУБД

ИТ-продукт = код + данные + инфраструктура + процессы.

## Информационные системы

Функции информационных систем:

- сбор
- обработка
- передача
- хранение
- представление информации

Люди не могут однозначно определить, что такое информация. В лекции это понятие разделяется так:

- **сигнал** - информация без смысла, ее физическое представление
- **данные** - определение ниже
- **знания**

**Данные** по **ISO/IEC 2382:2015** - поддающееся многократной интерпретации представление информации в формализованном виде, пригодное для передачи, интерпретации и обработки.

## Зачем нужна модель данных

*_Пример._* Базовая связь:

```text
студент -> группа -> преподаватель
```

По этой цепочке можно отобразить всех студентов преподавателя.

**НО!** Есть плохой пример с английским языком: студент напрямую указывает на преподавателя. Это исключение создает проблему с целостностью данных.

Таких исключений может быть много. Для них нужна **модель**, которая валидно обрабатывает ошибки ввода, обработки и интерпретации.

```text
бумажка -> Word -> таблицы -> система (хэш, бинарное дерево и т.п.)
```

На каждом этапе можно нарушить безопасность: например, перепутать хэш студентов.

### Вариант 1. Одна таблица

*_Пример._*

| студент | группа | дисциплина | преподаватель |
| --- | --- | --- | --- |
|  |  |  |  |

Проблемы:

- целостность: минимальная ошибка приведет к падению системы
- память

### Вариант 2. Несколько дисциплин в одной строке

| студент | группа | дисциплина_1 | преподаватель | дисциплина_2 | преподаватель_2 |
| --- | --- | --- | --- | --- | --- |
|  |  |  |  |  |  |

Проблема - еще больше памяти.

### Вариант 3. Отдельные таблицы

| студент |
| --- |
|  |

| группа |
| --- |
|  |

| дисциплина |
| --- |
|  |

Проблема - производительность: для сортировки и прочего нужно много `JOIN`-ов.

## СУБД

```text
клиент -> данные <- клиент
```

Такая концепция плохая: клиенты обращаются к данным напрямую.

**СУБД** - абстракция, или прослойка, между данными и клиентами.
