# Четвертая лекция. Устройство реляционной модели БД и реляционная алгебра

*Конспект дополнен по авторским пометкам. Данные в примерах условные; SQL-примеры используют синтаксис PostgreSQL. Ссылки ведут к источникам уточнений.*

## Отношение

В реляционной модели данные описываются через множества и отношения. Значения атрибутов берутся из заданных доменов, а строки объединяются в отношение. Общая математическая основа позволяет одинаково работать с данными о студентах, группах и других сущностях.

*_Пример._* Есть таблицы «Студент» и «Группа».

Таблица «Студент»:

| ИСУ | ФИО | № группы |
| --- | --- | --- |
| 100001 | Иванов Иван | K3201 |
| 100002 | Петров Петр | K3201 |
| 100003 | Сидорова Анна | K3202 |

Таблица «Группа»:

| № группы | Староста | Баллы |
| --- | --- | --- |
| K3201 | Иванов Иван | 80 |
| K3202 | Сидорова Анна | 90 |

Простраиваем связь `Студент -> Группа` по номеру группы. Иванов и Петров связаны с одной строкой группы `K3201`.

В SQL ниже используем имена `Student(isu, full_name, group_no)` и `Groups(group_no, leader, points)`.

Основные понятия:

- **Кортеж** - строка таблицы.
- **Схема отношения** - имя отношения и набор его атрибутов с соответствующими доменами. В таблице имена атрибутов видны в заголовке.
- **Домен** - множество допустимых значений для атрибутов.
- **Поле** - ячейка в таблице.
- **Степень отношения** - количество атрибутов.

Пусть заданы домены $D_1, D_2, \ldots, D_n$. Кортеж состоит из значений соответствующих доменов, а отношение $R$ - множество таких кортежей:

$$
(d_1, d_2, \ldots, d_n), \qquad d_i \in D_i,
$$

$$
R \subseteq D_1 \times D_2 \times \cdots \times D_n.
$$

То есть **отношение - не одна строка**, а множество строк. У отношения «Студент» степень равна трем. [Э. Ф. Кодд: реляционная модель](https://db.dobo.sk/wp-content/uploads/2015/11/Codd_1970_A_relational_model.pdf).

## Реляционная модель и SQL

SQL появился в IBM при разработке практической реляционной системы System R. Задача состояла в том, чтобы сделать работу с отношениями удобной и достаточно производительной. Поэтому формулировка «математическую модель невозможно реализовать» неверна: System R как раз продемонстрировала возможность такой реализации. [IBM Research: история System R](https://research.ibm.com/publications/a-history-and-evaluation-of-system-r).

Фразу **«SQL по мотивам Кодда»** можно понимать так: язык опирается на реляционные идеи, но таблица SQL не во всем ведет себя как математическое отношение. Например, SQL допускает повторяющиеся строки и использует `NULL`.

### Атомарность и уникальность

**Каждый элемент должен быть атомарен:** в одной позиции кортежа находится одно значение соответствующего домена. Атомарность не означает, что над значением нельзя выполнять операции или рассматривать символы строки.

*_Пример._* Найдем студентов, чье ФИО начинается с «Иванов»:

```sql
SELECT isu, full_name
FROM Student
WHERE full_name LIKE 'Иванов%';
```

`%` обозначает любую последовательность символов, в том числе пустую, а `_` - ровно один символ. Так, шаблон `'И_анов%'` допускает любой второй символ. В PostgreSQL `ILIKE` выполняет сопоставление без учета регистра с учетом локали:

```sql
SELECT isu, full_name
FROM Student
WHERE full_name ILIKE 'иванов%';
```

Возможность проверить часть строки **сама по себе не нарушает атомарность**: ячейка по-прежнему содержит одно строковое значение. `ILIKE` - расширение PostgreSQL, а не свидетельство о первоначальной реализации SQL в IBM. [PostgreSQL: LIKE и ILIKE](https://www.postgresql.org/docs/current/functions-matching.html).

**В отношении каждый кортеж уникален.** В SQL результат запроса по умолчанию может содержать повторы.

*_Пример._* Запрос номеров групп:

```sql
SELECT group_no FROM Student;
```

даст два значения `K3201` и одно `K3202`. Чтобы получить только разные номера, используем:

```sql
SELECT DISTINCT group_no FROM Student;
```

Теперь останутся `K3201` и `K3202`. `DISTINCT` устраняет дубликаты по всему набору выбранных столбцов и не задает порядок результата. [PostgreSQL: DISTINCT](https://www.postgresql.org/docs/current/queries-select-lists.html).

Также отмечены требования к именам:

- имя **отношения** уникально в пределах реляционной схемы
- имя **атрибута** уникально в пределах отношения

### Домены и NULL

Значения одного атрибута берутся из **одного и того же домена**.

*_Пример._* Номер группы имеет один смысл и совместимый тип в `Student.group_no` и `Groups.group_no`. Но принадлежности строковому типу недостаточно: строка `K9999` может иметь правильный формат, хотя такой группы нет.

Допустимость ссылки на существующую группу задаем внешним ключом. Это точнее, чем называть текущий список групп доменом: **домен задает допустимые значения атрибута, а внешний ключ связывает данные двух отношений**.

`NULL` обозначает отсутствие известного значения. Это не ноль, не пустая строка и не обычное значение домена. В SQL оно может присутствовать в столбцах разных типов, если нет ограничения `NOT NULL`.

*_Пример._* У студента пока не указана группа. Условие `group_no = NULL` не найдет такую строку: результат обычного сравнения с `NULL` - `UNKNOWN`, а `WHERE` оставляет только строки с результатом `TRUE`. Нужна специальная проверка:

```sql
SELECT isu, full_name
FROM Student
WHERE group_no IS NULL;
```

Обратная проверка - `group_no IS NOT NULL`. В лекции эти операции названы «костылем»; технически это отдельные предикаты для работы с отсутствующим значением. [PostgreSQL: сравнения и NULL](https://www.postgresql.org/docs/current/functions-comparison.html).

### Порядок строк и атрибутов

**Порядок кортежей и порядок именованных атрибутов не меняют смысл отношения.** Столбцы можно переставить вместе с их именами и значениями.

В записи кортежа через декартово произведение позиции, однако, должны соответствовать выбранному порядку доменов. В SQL порядок столбцов результата задается списком `SELECT`, а для гарантированного порядка строк нужен `ORDER BY`.

## Ключи и целостность

### Сущностная целостность

**Сущностная целостность** требует однозначной идентификации каждой строки: первичный ключ уникален и ни один из его атрибутов не равен `NULL`.

*_Пример._* Два студента не могут иметь один и тот же ИСУ, а строка студента не должна оставаться без ИСУ, если он выбран первичным ключом. [IBM: целостность данных](https://www.redbooks.ibm.com/redbooks/pdfs/sg247111.pdf).

### Суперключ, потенциальный и первичный ключи

**Суперключ** - атрибут или множество атрибутов, единственным образом идентифицирующее кортеж.

Поскольку кортежи отношения уникальны, **полный набор его атрибутов всегда является суперключом**. Любое надмножество суперключа тоже является суперключом: добавление атрибутов не теряет уже имеющуюся уникальность.

*_Пример._* Если ИСУ по правилам системы уникален, суперключами будут `{ИСУ}`, `{ИСУ, ФИО}`, `{ИСУ, № группы}` и весь набор `{ИСУ, ФИО, № группы}`. Само по себе ФИО ключом не считаем: однофамильцы и полные тезки допустимы.

**Потенциальный ключ** (`candidate key`) - суперключ, ни одно собственное подмножество которого не является суперключом. Минимальность здесь означает, что нельзя убрать атрибут, сохранив уникальность.

*_Пример._* `{ИСУ}` - потенциальный ключ. `{ИСУ, ФИО}` - суперключ, но не потенциальный: ФИО можно убрать, и ИСУ по-прежнему однозначно определит студента. Уникальность должна следовать из правил системы, а не только случайно выполняться в трех строках примера.

**Первичный ключ** (`primary key`) - один из потенциальных ключей, выбранный для основной идентификации кортежей. В таблице студентов выбираем ИСУ, в таблице групп - номер группы.

### Внешний ключ и ссылочная целостность

**Внешний ключ** - атрибут или набор атрибутов отношения, ссылающийся на потенциальный ключ другого или того же самого отношения. В SQL обычно ссылаются на `PRIMARY KEY` либо подходящий `UNIQUE`.

*_Пример._* `Student.group_no` ссылается на `Groups.group_no`. У нескольких студентов может быть одна группа, поэтому внешний ключ не обязан быть уникальным в таблице студентов.

**Ссылочная целостность** означает, что непустая ссылка ведет к существующему значению ключа. Если связь необязательна, внешний ключ может быть `NULL`.

*_Пример._* Студенту можно указать `K3201`, поскольку такая группа есть. Значение `K9999` будет отклонено, если группы с этим номером нет. Удаление группы, на которую ссылаются студенты, также требует правила: запретить удаление или явно задать действие над ссылками. [IBM: ссылочная целостность](https://www.ibm.com/docs/en/db2-for-zos/12.0.0?topic=constraints-referential).

Ключи из примера можно задать так:

```sql
CREATE TABLE Groups (
    group_no text PRIMARY KEY,
    leader text,
    points integer
);

CREATE TABLE Student (
    isu integer PRIMARY KEY,
    full_name text,
    group_no text REFERENCES Groups (group_no)
);
```

Здесь `group_no` у студента может быть `NULL`. Для обязательной группы нужно добавить `NOT NULL`.

Для составного внешнего ключа формулировка «либо совпадение, либо все значения `NULL`» требует уточнения. В PostgreSQL обычный `MATCH SIMPLE` освобождает от проверки при `NULL` хотя бы в одном компоненте; `MATCH FULL` допускает отсутствие ссылки только когда **все** компоненты равны `NULL`. [PostgreSQL: первичные и внешние ключи](https://www.postgresql.org/docs/current/ddl-constraints.html).
